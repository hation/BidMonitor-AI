# 公告详情与中标/废标追踪 — 设计文档

- 日期：2026-11-23
- 状态：已确认
- 背景：借鉴 bids-spider 项目的公告内容处理与中标方信息追踪能力，落到本项目团队工作台（Web）
- 迭代边界：本次只做「公告内容与结构化字段」+「中标/废标结果采集与中标方追踪」；机会分析规则引擎与 AI 精读留待下一迭代

## 1. 需求与目标

工作台当前只收录公告标题、原始 URL、发布时间（README 明示"不提取正文、不展示截止时间/预算/招标单位；中标/成交/结果类公告不再入库"）。本次借鉴 bids-spider 更完善的能力：

| 能力 | 现状（BidMonitor-AI） | 目标（本次迭代） |
|---|---|---|
| 公告正文 | 仅标题/URL/发布时间 | 采集时后台异步补抓详情页正文（`content`） |
| 结构化字段 | deadline/budget/purchaser/agency/project_no 字段已在表中，但采集流程未接上 | 详情补抓后自动回填这些字段 |
| 中标方信息 | 结果公告被显式过滤，不入库 | 放开过滤，中标/废标公告入库，提取中标单位/中标金额 |
| 公告类型 | 已能分类（中标结果/废标终止等），但搜索强制排除结果类 | 默认全部显示，类型多选可筛选 |

## 2. 已确认的决策

- **详情抓取时机**：后台异步补抓（不阻塞采集主流程）。
- **结果公告入口**：放开现有过滤器（复用现有采集器，不新增独立结果采集器），依赖列表页含结果公告。
- **中标方提取**：规则 + 正则（不用 LLM）。
- **落地载体**：团队工作台（Web，`apps/workbench/bidmonitor_workbench`）。
- **结果公告展示**：搜索页默认全部显示（与招标公告并列）；公告类型多选增加中标/废标类型。
- **中标字段**：新增独立字段 `win_company`/`win_amount`，列表与详情页展示。
- **实现方案**：方案 A —— CollectionService 内置后台补抓线程，复用现有调度/限速/stop 机制。

## 3. 现状关键事实（已核实）

- `projects` 表已预置 `deadline/budget/purchaser/agency/project_no/content/attachments/detail_status/detail_fetched_at` 字段（`storage/workbench.py` 建表语句）。
- `collectors/detail.py` 的 `fetch_detail()` 已适配数十个省级/央企站点，`extract_fields()` 已能提取项目编号/采购人/代理机构/截止时间/预算——**只是采集流程未调用**（`/api/projects/{key}/detail` 返回 410）。
- `classify_notice` 已能识别"中标结果/废标终止"等类型；`is_result_notice` 用于过滤结果类。
- 过滤点共三处：
  1. `collectors/generic.py` `parse_listing`：`is_result_notice(title, kind)` 跳过
  2. `collectors/feeds.py`：结果公告过滤
  3. `storage/workbench.py` `search()`：`is_result_notice(p.title,p.notice_type)=0` 强制排除
- SQLite 无 ORM、无迁移框架，新列按 `industry`/`category` 的 `ALTER TABLE ADD COLUMN` 兼容模式处理。

## 4. 数据模型变更

`projects` 表新增两列（在 `__init__` 的建表语句中一并加入，并对存量库走 `ALTER TABLE` 兼容）：

| 字段 | 类型 | 含义 |
|---|---|---|
| `win_company` | TEXT NOT NULL DEFAULT '' | 中标单位名称（仅中标公告有值） |
| `win_amount` | TEXT NOT NULL DEFAULT '' | 中标金额（如 `286 万元`，格式与 `budget` 一致） |

公告类型多选扩展：`meta()` 的 `notice_types` 由 `DISCOVERY_TYPES`（已剔除结果类）改为**全量 `NOTICE_TYPES`**，使"中标结果/废标终止/合同公告/验收公告"可筛选。

## 5. 放开结果公告过滤（三处）

1. `collectors/generic.py` `parse_listing`：删除 `is_result_notice(title, kind)` 跳过条件，结果公告同样入库（`classify_notice` 仍会标记类型）。
2. `collectors/feeds.py`：删除结果公告过滤行。
3. `storage/workbench.py` `search()`：删除 `is_result_notice(p.title,p.notice_type)=0` 强制排除子句 → 默认全部显示。

> 注意：`is_result_notice` 函数本身保留（用于 `meta()` 统计与可能的后续配对），仅不再用于采集/搜索过滤。

## 6. 中标字段提取（detail.py）

在 `extract_fields()` 中新增两个提取（复用 `readable_text` 后的正文纯文本）：

- **中标单位**：正则匹配 `中标供应商|中标单位|成交供应商|成交单位|中标人|成交人` 等关键词 + 分隔符 + 公司名称（参考 bids-spider `utils/announce.py` 的 `_COMPANY_PATS` 6 模式：字段行冒号、表格 `供应商名称：`、带序号/无序号表格、通用冒号）。提取后经组织后缀校验（含"公司/集团/研究院/事务所"等后缀才采纳）。
- **中标金额**：正则 `中标金额[:：]?([\d,]+(?:\.\d+)?)\s*(亿元|万元|元)`，存为 `win_amount`（格式 `数值 单位`，与 `budget` 一致）。
- 提取结果随 `extract_detail` 返回，由 `set_detail` 写入 `projects`。

存量数据回填：提供一次性回填脚本（可选），扫描 `notice_type='中标结果'` 且 `win_company=''` 的公告，从已存 `content` 中重新提取（仿 bids-spider `backfill_meta` 思路，幂等可重复运行）。

## 7. 异步补抓线程（CollectionService）

### 架构

在 `CollectionService` 中新增 `detail_fetcher` 后台线程（daemon），随 `open()` 启动、`close()` 停止，与采集线程共用 `self.stop` 事件。

### 调度逻辑

- 循环扫描：`SELECT id,url FROM projects WHERE detail_status='pending' ORDER BY created_at ASC LIMIT 50`（每轮限量，避免一次性扫全库）。
- 对每条：`fetch_detail(url)` → `store.set_detail(key, data)`（`set_detail` 已存在，自动回填 content/deadline/budget/purchaser/project_no 等字段，`extract_fields` 新增的中标字段随 data 一并写入）。
- 抓取成功 → `detail_status='ready'`；失败 → `set_detail(key, error=...)`（置 `detail_status='error'` + `detail_error`）。
- 每轮结束 `sleep` 一个间隔（默认 3 秒），继续下一轮。
- 无待抓取项时延长休眠（默认 30 秒）再扫，避免空转。

### 限速与容错

- **令牌桶**：`workbench_settings` 存 `detail_rate_per_min`（默认 20 次/分），可调。
- **指数退避**：抓取返回 403/429/限流页时，暂停该 host 60s~30min（`detail_host_cooldowns` 字典，host→下次可抓时间），期间跳过该 host 的公告。
- **失败标记**：单条失败不阻塞队列，`detail_error` 记录原因，下轮重试；连续失败过多可临时整体休眠。
- **与采集互斥**：补抓线程不持有 `self.lock` 长时间运行；采集运行时补抓照常进行，两者通过 host 冷却避免对同一站点并发施压。

### 生命周期

- `open()`：启动 `detail_fetcher` 线程。
- `close()`：`self.stop.set()` + `join(timeout)` 优雅停止。
- 服务重启后：未完成的 `pending` 公告继续补抓（天然断点续传）。

## 8. API 与前端

### 接口

- `POST /api/projects/{key}/detail`：从 410 改为——若 `detail_status != 'ready'` 返回当前数据并触发一次后台补抓（`fetch_detail` 放后台线程执行，接口快速返回当前详情）；若已 ready 直接返回详情。前端"打开原文"行为不变。
- `GET /api/projects`、`GET /api/projects/{key}`：返回字段增加 `win_company`/`win_amount`。
- `GET /api/meta`：`notice_types` 改为全量 `NOTICE_TYPES`。

### 前端（web/index.html + app.js + app.css）

- 公告类型多选：直接由 `meta().notice_types` 驱动，自动获得中标/废标选项（无需改代码）。
- 搜索列表卡片：中标公告展示"中标单位 / 中标金额"（`project-meta` 区域增加两项，仅在 `win_company` 非空时显示）。
- 详情抽屉（detail-dialog）：新增"中标单位 / 中标金额"信息项（`info-grid`）。
- 样式复用既有 CSS 变量与类名，不自创色值。

2. **中标金额提取**：`中标金额：286 万元` → `win_amount='286 万元'`；元单位换算；无金额时为空。
3. **搜索默认含结果公告**：`search()` 默认返回含中标/废标公告，`notice_type='中标结果'` 可筛选。
4. **补抓线程**：伪造 pending 数据 + mock `fetch_detail`，断言补抓后 `detail_status='ready'` 且字段回填；失败置 error。
5. **限速**：令牌桶/指数退避逻辑单测（不真实请求）。

## 10. 明确不做（YAGNI）

- 不做中标公告与招标公告的项目级配对/关联展示（保留 `project_no` 字段，后续迭代可做）。
- 不做机会分析规则引擎、紧迫度分级、AI 精读标书（下一迭代）。
- 不引入 Elasticsearch / Playwright，保持 SQLite + 现有 requests 架构。
- 不新增独立结果采集器（依赖列表页含结果公告）。

## 11. 成功标准

1. 结果公告（中标/废标）入库并可搜索，公告类型多选可筛选。
2. 中标公告的 `win_company`/`win_amount` 被正则提取入库，列表与详情页可见。
3. 后台补抓线程能把 `pending` 公告抓成 `ready`，字段（正文/deadline/budget/purchaser）回填，失败不阻塞。
4. 现有测试全 PASS（含修正后），新增 `test_workbench_win.py` 全 PASS。
5. 工作台重启后未完成的补抓继续（断点续传）。
