# 机会分析规则引擎 — 设计文档

- 日期：2026-11-23
- 状态：已确认
- 背景：借鉴 bids-spider 的个人业务机会分析能力（`analyze_opportunities.py` 的规则引擎），落到本项目团队工作台（Web）
- 迭代边界：本迭代只做「机会分析规则引擎」；AI 精读标书留待下一迭代

## 1. 需求与目标

工作台已能采集公告、提取详情（deadline/budget/content）并追踪中标。但每天上千条公告里只有少数几条与用户业务（服务器/IT/AI 销售方向）相关，逐条翻找效率低。本迭代借鉴 bids-spider 的规则引擎，自动给每条公告打"相关度"与"紧迫度"标记，并支持按相关度筛选。

| 能力 | 现状（BidMonitor-AI） | 目标（本迭代） |
|---|---|---|
| 相关度分级 | 无 | 直接相关 / 相关 / 意向线索 三档 + 排除词过滤 |
| 紧迫度分级 | 无 | 按投标截止天数 🔴≤7 / 🟡8-14 / 🟢>14 / ⛔已过期 / 未提取截止 |
| 关键词配置 | 无 | 复用 bids-spider 服务器/IT/AI 三档词表，存 workbench_settings |
| 界面展示 | 无 | 融入现有搜索页：相关度标签 + 紧迫度徽章 + 相关度筛选 |

## 2. 已确认的决策

- **业务方向/关键词**：复用 bids-spider 的服务器/IT/AI 三档关键词配置。
- **展示形态**：融入现有搜索页（不新增独立页面），列表卡片加标签/徽章，筛选区加"相关度"下拉。
- **紧迫度基准**：按投标截止时间（`deadline` 字段）算距今天数；无 deadline 显示"未提取截止"。
- **线索联动**：不联动——机会分析只标记/展示，用户手动加入线索池。
- **实现方案**：方案 A —— 存储层计算 + 搜索页筛选，配置进 `workbench_settings`，结果实时计算不落库。

## 3. 现状关键事实（已核实）

- `projects` 表已有 `deadline`（投标截止）、`budget`、`content`（详情正文，由 DetailFetcher 后台回填）、`win_company` 等字段。
- `storage/workbench.py::search()` 已支持 notice_type/industry/category/availability 筛选，返回 `substr(p.content,1,160) AS excerpt`。
- 关键词配置模式已有先例：`collection_schedule`/`custom_sources` 存 `workbench_settings`（JSON 值）。
- bids-spider 规则引擎已探明：`match_keywords(title, core, sec, excl)`（排除词优先→剔除；核心→直接相关；次要→相关）、`body_core_leads`（正文前 4000 字命中 ≥3 个不同核心词且排除词 <2 次 → 意向线索）、`urgency(days)`（<0 已过期 / ≤7 立刻 / ≤14 抓紧 / 其余从容）。
- 前端 app.js 已有 `tag()` 组件（绿色/橙色/紫色等）与搜索筛选区，可复用。

## 5. 关键词配置（`workbench_settings`）

- key = `opportunity_keywords`，值为 JSON：

- 本迭代不做界面编辑（YAGNI）；如需调整可改库或后续加界面。

## 6. 存储层接入（`WorkbenchStore`）

- `search()` 每条返回记录追加三字段：`relevance`（direct/related/leads/''）、`urgency_level`、`days_left`。
- 计算用 `classify(title, content, deadline, conf, today)`：`content` 取数据库原值（`search` 已 SELECT `substr(content,1,160)` 作 excerpt，相关度计算需完整 content——需在 SELECT 中同时取 `p.content` 或单独计算；为控制传输量，**相关度在存储层用完整 content 计算后只把 relevance/urgency 附加到返回行**，不返回 content）。
- `search()` 新增 `relevance` 参数：`''`（全部）/ `direct` / `related` / `leads`。SQL 查询后按该值 Python 过滤（因为 relevance 是计算值，无法走 SQL LIKE）。
- 计算量控制：`content` 为空时跳过 `body_core_leads`；正文只取前 4000 字符。

## 7. API 调整

- `GET /api/projects` 新增 `relevance` 查询参数（透传 search）。
- `GET /api/meta` 返回 `opportunity_keywords` 配置（供前端展示关键词来源；本迭代前端不编辑）。

## 8. 前端（`web/index.html` + `web/assets/app.js`）

- 搜索筛选区新增"相关度"下拉：全部 / 🔴 直接相关 / 🟢 相关 / 💡 意向线索。
- 列表卡片 `card-top` 区域新增：
  - 相关度标签：直接相关 → `tag('直接相关','green')`；相关 → `tag('相关')`（默认蓝）；意向线索 → `tag('意向线索','orange')`。
  - 紧迫度徽章：`🔴 距截止X天`（urgent）/ `🟡 距截止X天`（prep）/ `🟢 距截止X天`（relaxed）/ `⛔已过期`（expired）/ `未提取截止`（unknown）。
- 复用既有 CSS 变量与 `tag` 组件，不自创色值。

## 9. 测试（新增 `tests/test_opportunity.py`）

1. `match_keywords`：排除词优先剔除；核心词 → direct；次要词 → related；无命中 → ''。
2. `body_core_leads`：正文 3 个不同核心词 → leads；排除词命中 ≥2 → 不判定；正文不足 → ''。
3. `urgency`：deadline 空 → unknown；已过期 → expired；7 天内 → urgent；8-14 天 → prep；>14 → relaxed。
4. `classify` 组合输出三字段。
5. `search(relevance='direct')` 只返回直接相关公告（集成测试）。
6. `WorkbenchStore.__init__` 默认写入 opportunity_keywords。
